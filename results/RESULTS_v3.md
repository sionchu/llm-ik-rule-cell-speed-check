# 소포 분류 셀 v3: 젖은 얼룩 놓침 개선 (2026-11-12)

저장된 예측(pred_*.jsonl)으로만 오프라인 평가. 새 API 호출 0건(Decisions·Opus·Fable 모두). 임계값은 stream 200건에서만 정하고 hard 100건에 그대로 적용.
스크립트: `img/damage_check_v3.py`(특징), `img/eval_v3.py`(케이스 비교). 결과: `results/v3_eval.json`.

## 결론
- 놓친 원인은 "옅은 얼룩"이 아니라 **기존 파손 검사의 기준 버그**. 기존 검사는 상자 밝기 *중앙값* 대비 어두운 픽셀을 셌는데, 얼룩이 뚜껑을 넓게 덮으면 중앙값 자체가 얼룩색이 되어 점수가 0에 가깝게 나옴(stream_0172: 얼룩이 뚜껑 절반인데 0.008). 이미지로 보면 얼룩은 뚜렷함.
- 상대 밝기 대신 **얼룩의 절대 색**(중간 밝기 + 갈색, 노란 가이드 제외)과 **찢김 안쪽 색**(회갈색)을 세는 v3 검사로 바꾸면, hard에서 **파손 21/21, 정답 99/100**, Opus로 보내는 비율 **36% → 18%**, 평균 시간 **4.2 → 3.3 s**, 비용 **절반**.
- 하한·상한 비율 튜닝(B안)은 Opus 비율만 늘고 효과가 작거나(hard +2) 상한을 내리면 정상 소포를 반품으로 보냄(stream 오반품 9). 원인이 기준 버그라 임계값으로는 못 고침.
- Fable 승격(E안)은 v3에서 정확도 이득 없음, 비용 2배(추정). **Fable 새 호출 안 함.**

## 한계
- **합성 렌더 한계**: 셋의 젖은 얼룩은 단색 타원이라 색 분리도가 200배 이상 나옴. 실제 박스(인쇄 무늬, 테이프 색, 조명, 갈색 박스)에서는 이렇게 깨끗하게 갈리지 않음. 실데이터 검증 NOT_RUN.
- **설계 누설 가능성**: 임계값은 stream에서만 정했지만, 특징 색 범위는 놓친 건(hard 포함) 이미지를 보고 잡음. 엄밀한 홀드아웃은 아님 → 새 셋 생성(Isaac 렌더 필요) NOT_RUN. 이번엔 다른 Isaac 프로세스와 겹칠 수 있어 렌더 안 함.
- 찢김색 분리도는 약 5배(stream 0.0033 vs 0.018)로 얼룩색보다 얇음.
- Fable 비용은 Opus의 2배로 추정(CLI 기록 비용 비율). 직접 API 단가 실측 NOT_RUN.
- Decisions 재호출 없음(키 없음). FC 셋 평가 NOT_RUN.
- 1~2 s 사이클 목표에는 아직 못 미침: hard p50 2.95 s, Opus 18%. 다음 단계는 RESCAN 오답 원인(라벨 일부 가림) 확인과 Opus 승격 조건 축소.
